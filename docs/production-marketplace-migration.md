# Marketplace 单库原地迁移

迁移命令只连接 `MYSQL_DSN` 指向的当前数据库，在这个库里完成专家团、专家、Skill/MCP 的拆分、去重、版本和引用更新。生产数据复制到 test 是运行前的环境准备，不能通过这个命令导出、恢复或跨库同步。命令不部署服务、不修改三个功能开关、不自动升级业务表结构。

## 运行

旧的 `plugin-backfill`、`marketplace-stock-migration` 命令、专属实现与旧 backfill 镜像入口已删除。资源转换统一使用本文命令；数据库历史 SQL 与旧审计记录继续保留。

```sh
go build -o /tmp/marketplace-migrate ./cmd/marketplace-migrate

# 默认只预览，不写数据库、对象或恢复文件。
/tmp/marketplace-migrate --database CURRENT_DATABASE --policy /secure/policy.json

# 一次执行；中断后用完全相同的参数重试。
/tmp/marketplace-migrate --database CURRENT_DATABASE --policy /secure/policy.json \
  --apply --state-file /secure/marketplace-run.state

# 对同一次执行做只读复核。
/tmp/marketplace-migrate --database CURRENT_DATABASE --policy /secure/policy.json \
  --verify --state-file /secure/marketplace-run.state
```

使用 Marketplace 服务已有的环境变量：`MYSQL_DSN`、`STORAGE_DRIVER`；本地存储用 `LOCAL_STORAGE_DIR`，OSS/S3 用 `OSS_ENDPOINT`、`OSS_BUCKET`、`OSS_ACCESS_KEY`、`OSS_SECRET_KEY`，以及原有 `OSS_REGION`、`OSS_KEY_PREFIX`、`OSS_PATH_STYLE`。必须使用当前环境实际的对象存储配置。凭据通过环境安全注入，不放在命令参数、文档或 Git 中。

本地模式要求 `LOCAL_STORAGE_DIR` 已存在（默认 `/tmp/marketplace-uploads`），且必须指向现有服务实际使用的附件目录。目录不存在会在读取数据库前报 `storage_configuration_failed`；命令不会自动创建空目录，以免把错误的存储配置误当成空库存。仅在准备全新空白演练环境时，由操作员事先创建目录；生产数据副本必须先同步真实附件。

`--database` 必须与连接串及服务器返回的当前库名一致；首次执行还将实际数据库名、MySQL server UUID、存储位置和选择规则绑定到恢复文件，重试不能换库或存储。没有生产库名称限制，也没有所谓原库、目标库。连接强制使用 UTC 会话，禁止多语句等不必要的连接选项。

恢复文件是本次计划与必要文件字节的私有断点，不是整库备份；以 0600 权限创建、校验摘要且拒绝覆盖。SHA256 只用于检测意外损坏，不是签名或 MAC，不能抵御有权限修改该文件的进程。恢复文件与迁移程序、数据库及存储凭据属于同一受信任操作边界；不得接收其他用户提供的断点，操作员及其进程必须可信。它可能包含 MCP 配置和附件，必须保存在受控目录，禁止提交 Git。首次执行前保存，重试读取同一计划，避免根据已被迁移的数据重新生成 ID。不要删除文件后重新规划一个已部分执行的库。

## 转换规则

- 按“平台共有、每个 Space、私有 owner”分别处理，禁止跨 Space 合并或扩大权限。系统 Skill、MCP、专家、专家团均保持平台共有，不能为了附件或拆分归入某个 Space。
- 已发布资源先解析专家团及专家中的依赖，写入时按 Skill/MCP、专家、专家团的顺序执行，引用指向明确的已发布版本。尚未发布的草稿分别拆成独立草稿，不建立任何依赖或恢复关系文件、不生成 release；原始关系只保留在原有历史数据。后续由用户先发布 Skill，再让专家引用已发布 Skill 并发布，最后由专家团引用已发布专家。保存无成员的独立草稿允许通过，正式引用、发布及安装的已发布版本校验不放宽。
- 旧关系的 `source_index` 不进入新版关系元数据，排序继续使用 `sort_order`；成员的 `member_key`、`role`、`is_leader` 保留，并按新版引用规则校验。无法识别的其他关系字段阻断迁移，不静默丢弃。
- 专家原有 `expert/context.json` 逐字节保存在 `migration/legacy/expert/context.json`，避免保留新版禁止的旧内嵌能力入口；成员角色和负责人仍由专家团关系表达。归档路径已存在时阻断，禁止覆盖。原始历史版本不修改。
- `frontend-dev` 选择中文版本。可在 policy 中通过源资源 ID 明确指定；未能明确选择时阻断并报告，不随意取英文版本。
- `fullstack-dev` 的不同内容各自保留；`wechat-article-search` 与 `online-search` 的不同实现各自保留。其他同名资源在同一归属范围内按 `updated_at` 从早到晚选择第一份，相同时按 ID 排序。资源映射用于同步修正引用。
- MCP 的地址、认证、服务配置值及扩展字段保留；只有冲突的内部服务键会在目标包中按来源改名，不替换成 test 地址、不调用 MCP 服务。这是本次单库转换的明确保留策略，替代旧 backfill 清空 env/headers 的行为；不承诺将已有明文凭据变成 secret references。新 connector 继承来源的 owner、Space、visibility 和目录状态，不能扩大读取范围；真实 MySQL 回归检查持久化后的配置及 system/space/private 的同一组调用者权限。空 `mcp.json` 也从专家当前文件及快照中清理，不因没有生成 connector 而保留旧内嵌入口。同一 owner、归属范围及生命周期内，显示名、完整有效 MCP 配置、全部附件的路径/规范 MIME/内容字节、manifest 语义及非附件包配置全部等价的 Connector 才统一为一份，所有当前引用更新到该目标，保留全部来源证据。地址、认证、根/服务扩展字段参与配置比较，不跨 Space 或 owner 合并。各自保留的 Connector 只有在同一专家/专家团安装闭包中显示名冲突时，市场显示名与安装引用名才加上来源名称后缀（如 `search-高级开发专家`）；来源名称仍重名时追加稳定短标识，并在数据库和安装名称长度限制内截断。显示名去重只更新目标显示名与 manifest 名称，内部服务键改名另按下述规则执行；引用仍按各自资源 ID 对接，地址、认证、扩展值与支持文件字节不变；目标 `mcp.json` 若因内部服务键冲突而改名，会保留原文和键名映射在私有断点中，源记录与原历史仍不改动。互不相关的安装闭包与空间不因全局同名而被重命名。执行和恢复仍以 `connector_name_ambiguous` 拦截任何残留的安装闭包重名。默认安装按每个专家合并 MCP 服务键；若同一专家引用两个不同 Connector，而它们的 `mcpServers` 含有相同服务键，两份资源各自保留，目标服务键按原键、来源名称的合法 ASCII 部分与稳定短标识生成不同别名。只移动 `mcpServers` 的键，不改其对应的地址、认证、参数、环境变量或任何扩展值；所有结构化引用继续按各自目标资源 ID 对接。Apply/Verify 同时复核目标文件与包配置是否恰好等于原文的键名投影；残余冲突以 `connector_server_key_conflict` 阻断，任何配置值变化以 `mcp_alias_projection_mismatch` 阻断。不同专家各自使用相同服务键不冲突。这里仅预检该重复键边界，其他旧配置扩展仍按原配置保留，不承诺默认安装能消费所有历史扩展；真实安装验收继续单独进行。
旧内嵌 Skill 的市场简介为空时，仅从原始 `SKILL.md` 的合法 YAML `description` 字段补齐；已有简介保留。不会自动将任意正文段落发布为目录简介。文件头缺失、无效或简介为空时，报告 `skill_description_unavailable`，由操作者在 policy 的 `CatalogDescriptions` 中按源 Skill ID 提供明确目录简介和 `SourcePackageHash`（源 manifest/package 的标准 PluginHash）。简介与源内容摘要不匹配则拒绝。原始正文、文件及历史版本保持不变。
- 保留已有历史版本，新建有效版本及发布记录，更新当前版本、发布指针和固定版本引用。内部 `plugin_versions.version` 是后端使用的快照序号（如 `1`）；业务版本 `declared_version`、`current_version` 和发布记录的 `version_label` 使用合法三段式（如 `1.0.0`）。不能只改一个字符串就认定解决 `released_version_required`，还要核对发布记录和引用 ID。
- 平台附件写入 `platform/plugins/<最终资源ID>/attachments/versions/<SHA256>`，Space 附件使用对应 Space 路径。脚本和后端统一检查归属、文件长度与 SHA256；下载、历史版本、安装及保存版本均使用这套规则。
- 旧 `public` 平台资源在目标记录中统一为 `system`，新附件始终写入平台路径；旧记录原有的 Space 附件仍按实际归属读取。旧 `skills/`、`experts/`、`squads/` 路径必须与源记录 ID 或原始回填的确定性 ID 映射吻合；内嵌 Skill 还需证明专家/成员及 Skill 的具体目录。其他资源、兄弟 Skill、不同成员或无法证明来源的路径，在首次对象读取前阻断，不凭目录前缀猜测归属。
- 文件预算与服务默认读取规则一致：单文件不超过 20 MiB，单资源全部文件累计不超过 100 MiB；超限在计划阶段阻断，不生成迁移成功但无法下载或再次保存的版本。
- `storage` 附件必须声明非负整数 `content_size` 和规范的 `sha256:` 小写摘要 `content_hash`，缺失或不匹配会阻断计划；合法空文件大小为 0，仍需声明空内容摘要。不能用迁移时现读的字节反填摘要来绕过源声明校验。历史 `skill/ref.json` 中原本没有声明摘要的旧指针，仍记录读取后的快照证据并在写入前复核。
- 每个资源的源对象按 key 去重，声明校验与文件解析共用缓存及累计读取预算；单个普通对象读取不超过 20 MiB，ZIP 对象不超过 100 MiB，全部不同源对象累计不超过 100 MiB。网络读取仅允许额外 1 字节探测超限，超限字节不进入缓存；展开后的文件另按上面的单文件和累计预算检查。
- 完成回执包含目标资源的审核记录；回执写入后审核记录新增、删除或修改，都会使恢复/最终校验失败。迁移和验收期间仍需暂停其他写入。

可选 policy 格式：

```json
{"FrontendChineseSourceIDs":["中文版本源资源ID"]}
```

## 执行与验证边界

请使用迁移前完整数据验证。若市场描述为空但完整原文件头仍有 description，新脚本可以据原文补齐该字段；若原文件、文件头或成员关系已丢失，新脚本不能凭空恢复缺失内容；需要从完好的生产数据副本或备份重新准备 test，再核对四类资源的卡片信息、可见性和专家团拆分结果。

复制线上旧库到 test 后，先由配套新版 Marketplace 后端按正常启动流程完成业务表升级，再运行数据迁移。脚本不会代替后端升级结构。读取业务输入使用单个 Repeatable Read 只读事务；写入前检查所需业务表结构。实际执行创建三个迁移进度/映射表，以每个资源的事务提交保存断点，禁止冲突覆盖。对象先以不可变方式写入并回读校验，再写入数据库；失败后使用同一恢复文件重试。历史文件和已有版本不删除。

计划捕获 `plugins` 源记录的完整列摘要，包括 NULL 与空值的区别；每个未完成资源在行锁内重新比对后才可写入。分类、标签、图标、发布者等任意列变化都会阻断旧计划。同时捕获源依赖关系、全部版本与发布记录、审核状态、展示配置、版本引用索引、索引校验状态和审计记录。执行时在 Repeatable Read 事务内锁住对应记录及范围，逐项比对后才可写入；合并到同一资源的其他同名来源也接受同样检查。对象写入前先完整预检未完成资源的源记录与关联库存；同一次执行已提交的资源通过回执复核，不会误用原始快照阻止续跑。事务内仍会再次校验。恢复文件格式为 v8，拒绝旧格式，防止沿用缺少完整 Connector 文件树与 MCP 服务键改名证据的旧计划。已经部分执行的旧断点不能删除、手改版本或重新规划；应保留现场，恢复演练副本或按既定备份方案恢复后再使用新版。

执行记录的结构指纹同时覆盖字段及其默认值、表引擎/排序规则、索引（含唯一性、前缀和表达式）、主键/唯一约束、外键目标及更新删除规则、CHECK 表达式与启用状态。任一元数据查询失败均阻断恢复。自动递增计数和索引统计不参与指纹，普通行写入不会被误判为结构变化。

数据库元数据在只读 Repeatable Read 事务中读取；对象存储读取在该事务提交后进行，两者不是共同快照。附件若有源摘要/长度声明则逐项核验；无论源是否带有声明，都会记录实际读取对象的完整 SHA256 和长度，解析文件字节也绑定到私有恢复文件。写入目标对象前重新读取并核对所有源对象，每个未完成资源在数据库事务内再次检查其源对象；同一地址的文件被替换、丢失或校验不符都会停止。恢复继续使用原计划，不会用后来读到的新内容覆盖断点。源存储与数据库仍没有共同事务，因此整个计划和执行期间必须暂停附件上传、替换及外部对象写入。

运行期间应暂停 Marketplace 写入；命令的数据库锁只防止重复运行本命令，不能阻止业务服务编辑。原地迁移的数据库备份及恢复方案由运行环境另行准备；本工具不承担备份职责。

失败不代表整次执行已经回滚：对象存储与数据库没有共同事务，数据库也是逐个资源提交。中断可能留下已写入但暂未引用的不可变对象，以及已完成的前序资源。恢复文件保存本次完整对象清单、摘要和必要字节；数据库进度表保存已提交资源的校验回执。保留该文件，用原命令重试：已有对象必须通过内容校验才可复用，已提交资源必须通过回执校验才会跳过，未完成资源继续执行。不要删除进度表或恢复文件，也不要手动删除历史对象。若遇到源数据变化、对象内容冲突或回执不符，应停止写入并核对变化；无法恢复原计划时，按运行前备份方案恢复数据库及对应存储后重新执行，不能换一个新恢复文件强行继续。

失败结果明确包含 `keep_state_file=true`、`objects_may_remain=true` 和恢复指引。数据库失败结果另含 `commit_state`（`none`、`partial` 或无法查询时的 `unknown`）、已持久化回执对应的 `committed_ids`、失败资源 ID；这些回执 ID 不表示失败后的数据已重新验收。`complete=false` 不能理解为整次回滚。重复执行仍遇到相同数据/约束冲突时保持停止，先核对并恢复原计划所依赖的条件；无法安全恢复时，使用运行前数据库及对象存储备份恢复环境，不能丢弃旧断点强行重新规划。

恢复文件中的计划本身就是持久化对象清单：在第一次对象写入前，已保存所有目标对象键、完整 SHA256 所需的文件字节、长度及版本附件摘要。执行进度不靠可能过时的本地布尔标记判断；`--verify` 根据这份清单只读核对对象存储，在 `object_inventory` 中列出每个对象的 `verified`、`missing` 或 `verification_failed` 状态。权限/网络错误不会被当成对象不存在。中断后，同一恢复文件能重新列出完整期望清单并复用已校验对象。对象字节通过校验不代表已有数据库引用；需结合数据库回执和最终引用校验判定整个迁移完成，不能仅凭缺少本次回执删除对象，已有历史版本可能仍在引用它。工具不自动删除不可变对象；无法继续的演练可重新准备完整 test 副本，生产恢复使用预先准备的备份方案。

`complete=true` 表示本次计划的数据库、版本、发布、引用及对象校验完成；`install_verified=false` 明确表示尚未完成真实安装验收。仍需在 test 检查平台/Space 可见性、历史下载、专家及专家团安装、MCP 配置保留和重试行为。生产数据复制到 test 时，数据库及其引用的附件都应可读取，并保持 test 的业务连接配置指向 test。

## 本地检查

```sh
go test ./cmd/marketplace-migrate ./internal/migration/...
go test -race -shuffle=on -count=1 ./...
go vet ./...
```

`internal/migration` 的真实 MySQL 集成测试仅在设置 `MIGRATION_TEST_MYSQL_DSN` 时运行，测试连接必须使用 `octo_marketplace_rehearsal_` 前缀的专用测试库。这个限制只属于会创建、删除临时库的测试夹具，不限制实际迁移命令的库名。未设置时跳过，不能据此声称已经在真实 MySQL 或集群完成迁移。

分类表是独立的市场展示策略，分类本身的可见性/排序与某个资源的可见性/排序不要求相等。原有注册只有在完整快照校验后才保留，不用资源配置覆盖；缺失注册按首个资源的已校验展示配置补建。本次新建的同一注册若被后续资源复用，可见性/排序必须一致，否则阻断；时间字段保留首次建档值。共享行按唯一键锁定并明确处理，不使用 INSERT IGNORE 静默吞掉冲突。

本次新建、原始分类快照中尚不存在的注册，其完整行通过首次提交资源的完成回执保存摘要：`stateHash` 查询 `SELECT c.*`，并与注册插入在同一事务提交。后续资源提交前及最终验证通过 `verifyCategorySnapshot → verifyReceipt → stateHash` 重新比对；不是只检查注册 ID 或关联存在。注册 ID、场景、资源类型、分类、可见性、顺序、创建/更新时间变化或整行删除，均应阻断恢复及成功报告。真实 MySQL 回归 `TestApplyMySQLNewCategoryFullRowDriftBetweenNodeCommits` 覆盖逐字段修改、两次资源提交之间的检查、恢复原行后继续成功及完成后的再次篡改。

分类整行被删除后不会出现在“新增注册”列表中，因此另从本次已完成资源的展示配置检查所需分类注册仍然存在，资源类型取自冻结计划。该检查在下一个资源事务写入前执行，避免缺失注册被后续资源静默重新补建；首次只读预检尚无回执表时不要求创建迁移管理表。

共享分类注册在同一输入事务中完整冻结；执行前和每个资源写入事务内锁表内记录并比对摘要，任何外部增删改均阻断。该检查也会保守阻断其他分类的运营调整，因此运行期间必须暂停全部市场写入。只有本次计划前序资源已提交、确定性 ID 和回执校验均匹配的新增分类注册允许续跑。v8 断点拒绝缺少共享分类快照的旧断点；已部分执行的旧计划不得手改版本号或删除重跑。

完成资源的回执快速路径和最终 Verify 都重新检查完整分类快照；缺少分类快照的 Apply/Verify 计划一律拒绝。旧 Skill 存在可信 object_key 时，必须有 object_key_hash（SHA256）及 object_key_size，读取缺失、超限或摘要不符均报错，不回退到占位正文。缺少这些断言的旧记录需从完好的原始数据执行迁移；不能在下载时给当前未知内容临时补摘要并视为可信。
